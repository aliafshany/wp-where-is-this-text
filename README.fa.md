# این متن کجاست؟ (Where Is This Text)

**متن را روی سایت می‌بینید، ولی وردپرس به شما نمی‌گوید از کدام صفحه ویرایش می‌شود.**

این افزونه دقیقاً همین را حل می‌کند. یک خط از متنی را که روی سایت می‌بینید بچسبانید؛ افزونه می‌گوید آن متن کجا ذخیره شده و یک دکمه می‌دهد که مستقیم شما را به همان صفحهٔ ویرایش می‌برد.

این افزونه فقط **می‌خواند**. هیچ‌وقت چیزی را تغییر نمی‌دهد.

## مسئله چیست؟

یک جمله روی سایت دیده می‌شود. از کجا می‌آید؟ می‌تواند هر کدام از این‌ها باشد:

- یک نوشته، برگه یا محصول
- یک **ابزارک** در یکی از ناحیه‌هایی که اسمش را فراموش کرده‌اید
- یک **تنظیم قالب** که داخل یک ردیف سریالایزشدهٔ بزرگ ذخیره شده
- **توضیح یک دسته‌بندی** یا یک فیلد سفارشی روی آن
- متنی داخل یک چیدمان **المنتور**

وردپرس هیچ جایی برای پیدا کردن این‌ها ندارد. جست‌وجوی پیشخوان فقط نوشته‌ها را می‌گردد.

افزونه‌های جست‌وجو و جایگزینی، رشته را داخل دیتابیس **پیدا می‌کنند** — اما فقط برای منبع‌هایی می‌توانند لینک ویرایش بسازند که اصلاً صفحهٔ ویرایش دارند: نوشته‌ها، دیدگاه‌ها و کاربران. نتیجه‌ای که در `wp_options` پیدا شود، فقط با نام ستون برمی‌گردد و هیچ چیزی برای کلیک‌کردن ندارد، چون یک option اصلاً صفحهٔ ویرایش ندارد. در عمل می‌فهمید متن داخل چیزی به نام `widget_text` است و همچنان نمی‌دانید آن کجاست.

این افزونه همان قدم آخر را برمی‌دارد: ظرف را به صفحه‌ای که ویرایشش می‌کند وصل می‌کند.

## دو کاری که جست‌وجوی ساده در دیتابیس نمی‌تواند بکند

### ۱. متن داخل صفحه‌سازها را پیدا می‌کند

صفحه‌سازها محتوا را به شکل JSON ذخیره می‌کنند و تابع `json_encode()` در پی‌اچ‌پی به‌صورت پیش‌فرض همهٔ نویسه‌های غیرِ ASCII را escape می‌کند. به همین دلیل داخل `_elementor_data` **هیچ متن فارسی خوانا وجود ندارد** — فقط دنباله‌هایی مثل `\uXXXX`.

پس جست‌وجو برای متنی که می‌بینید هیچ‌وقت به نتیجه نمی‌رسد. هیچ‌وقت. این دقیقاً دلیلی است که محتوای صفحه‌ساز برای همهٔ افزونه‌های آمادهٔ جست‌وجو نامرئی است، و مهم‌ترین دلیل ساخته‌شدن این افزونه.

این افزونه شکل escape‌شدهٔ JSON را هم کنار شکل عادی جست‌وجو می‌کند.

### ۲. حروف هم‌شکل را می‌فهمد

«ي» و «ك» عربی با «ی» و «ک» فارسی تقریباً یک‌شکل دیده می‌شوند ولی کدهای یونیکد متفاوتی دارند. متنی که با یک صفحه‌کلید تایپ شده با متنی که با آن یکی ذخیره شده مطابقت پیدا نمی‌کند. هر دو نگارش خودکار جست‌وجو می‌شوند.

## وقتی چیزی پیدا نشود، عبارت را کوتاه می‌کند

شایع‌ترین دلیل «هیچی پیدا نشد» این است که متن چسبانده‌شده مربوط به **دو فیلد جدا** است — مثلاً یک تیتر و زیرنویس زیرش. هیچ ردیفی در دیتابیس هر دو را با هم ندارد، پس جست‌وجوی دقیق درست عمل می‌کند و صفر نتیجه می‌دهد، ولی برای کاربر مثل خرابی به نظر می‌رسد.

وقتی کل خط به نتیجه نرسد، این افزونه خودکار با عبارت‌های کوتاه‌تر دوباره تلاش می‌کند (اول کلمه‌های آخر را حذف می‌کند، بعد کلمه‌های اول) و می‌گوید کدام عبارت کوتاه‌تر جواب داده:

> تمام خطی که چسباندید در هیچ ردیفی نبود — معمولاً یعنی دو فیلد جدا را پشت سر هم چسبانده‌اید. نتیجهٔ زیر برای این عبارت کوتاه‌تر است: **پرداخت امن و مطمئن**

ضمناً فقط از **اولین خط غیرخالی** چیزی که می‌چسبانید استفاده می‌کند، چون متن ذخیره‌شده بین پاراگراف‌ها خط جدید واقعی دارد ولی متن چسبانده‌شده آن را از دست می‌دهد.

## چه چیزهایی را می‌گردد و هر نتیجه کجا می‌برد

| منبع | شما را می‌برد به |
|---|---|
| `wp_posts` — عنوان، محتوا، چکیده | ویرایشگر همان نوشته/برگه/محصول، یا ویرایشگر **المنتور** اگر برگه با صفحه‌ساز ساخته شده باشد |
| `wp_postmeta` — فیلدهای سفارشی | صفحهٔ ویرایش همان مورد؛ `_elementor_data` مستقیم المنتور را باز می‌کند |
| `wp_options` — `widget_*` | نمایش ← ابزارک‌ها، با نام **ناحیه‌ای** که ابزارک در آن است و این‌که فعال است یا در «ابزارک‌های غیرفعال» افتاده |
| `wp_options` — `theme_mods_*` | نمایش ← سفارشی‌سازی |
| `wp_options` — `blogname` و `blogdescription` | تنظیمات ← همگانی |
| `wp_options` — `woocommerce_*` | ووکامرس ← تنظیمات |
| `wp_options` — بقیه | نامش را می‌گوید، با توضیح این‌که به صفحهٔ تنظیمات یک افزونه یا قالب تعلق دارد |
| `wp_termmeta` | صفحهٔ ویرایش همان دسته یا برچسب |
| `wp_term_taxonomy` — نام و توضیح | صفحهٔ ویرایش همان دسته یا برچسب |

نتیجه‌ها طوری مرتب می‌شوند که چیزهای زنده و قابل‌ویرایش اول بیایند و باقی‌ماندهٔ غیرفعال آخر.

## نصب

**به‌عنوان افزونهٔ معمولی**

۱. این مخزن را به‌صورت ZIP دانلود کنید.
۲. افزونه‌ها ← افزودن ← بارگذاری افزونه ← فایل ZIP را انتخاب کنید ← نصب ← فعال‌سازی.

**یا به‌عنوان افزونهٔ الزامی (mu-plugin)** — همیشه روشن، اشتباهی غیرفعال نمی‌شود

فایل `where-is-this-text.php` را داخل پوشهٔ `wp-content/mu-plugins/` کپی کنید. اگر این پوشه نیست، بسازید. نیازی به فعال‌سازی ندارد.

**یا با WP-CLI**

```bash
wp plugin install https://github.com/aliafshany/wp-where-is-this-text/archive/refs/heads/main.zip --activate
```

نیازمندی: وردپرس ۵.۶ به بالا و پی‌اچ‌پی ۷.۴ به بالا. بدون وابستگی، بدون مرحلهٔ build، بدون صفحهٔ تنظیمات.

## استفاده

به **ابزارها ← Where is this text?** بروید.

**فقط یک خط کوتاه** از متنی را که روی سایت می‌بینید بچسبانید و دکمهٔ پیدا کردن را بزنید.

یک جدول می‌گیرید: آن چیز چیست، از کدام صفحه ویرایش می‌شود، متن پیداشده در متن اطرافش، و یک دکمهٔ **باز کردن** که شما را همان‌جا می‌برد.

نکته‌ها:

- یک خط، نه چند پاراگراف.
- یک عبارت کوتاه و شاخص بهتر از یک عبارت طولانی جواب می‌دهد.
- اگر چیزی پیدا نشد، ممکن است متن داخل تصویر باشد، یا به‌جای ذخیره‌شدن در دیتابیس با کد تولید شود.

## ایمنی

این بخش مهم است، پس دقیق نوشته شده.

- **فقط خواندنی.** افزونه فقط `SELECT` اجرا می‌کند و یک جدول نشان می‌دهد. هیچ مسیری برای نوشتن در دیتابیس ندارد.
- **هیچ چیزی از سرور شما بیرون نمی‌رود.** بدون درخواست HTTP، بدون تله‌متری، بدون سرویس بیرونی.
- **هیچ ردی در بخش کاربری سایت ندارد.** تنها فراخوانی `add_action()` داخل شرط `is_admin()` است، پس درخواست یک بازدیدکنندهٔ عادی هیچ callback‌ای اضافه نمی‌کند و هیچ کوئری‌ای اجرا نمی‌کند. روی خروجی سایت، کش صفحه یا CDN شما اثری ندارد.
- **فقط برای مدیر.** دسترسی `manage_options` هم برای ثبت صفحه و هم دوباره هنگام نمایش بررسی می‌شود، و فرم nonce دارد.
- **امن در برابر تزریق.** همهٔ کوئری‌ها از `$wpdb->prepare()` به‌همراه `esc_like()` عبور می‌کنند. نام جدول‌ها از خصوصیت‌های `$wpdb` می‌آید.
- **امن در خروجی.** هر چیزی که نمایش داده می‌شود escape می‌شود — `esc_html()` برای متن و `esc_url()` برای پیوندها.
- **محدودشده.** تعداد ردیف‌ها برای همهٔ حالت‌های جست‌وجو روی هم سقف دارد، ستون‌های طولانی در خود SQL کوتاه می‌شوند، و عبارت‌های کمتر از ۳ نویسه رد می‌شوند.

حذف افزونه یعنی پاک‌کردن فایل. هیچ option‌ای ذخیره نمی‌کند، هیچ جدولی نمی‌سازد و چیزی از خودش باقی نمی‌گذارد.

## توسعه‌دادن

سه فیلتر، اگر لازم داشتید:

</div>

```php
// یک option را به صفحهٔ تنظیمات قالب خودتان وصل کنید.
// خیلی از قالب‌ها همهٔ تنظیمات را در یک option سریالایزشده نگه می‌دارند.
add_filter( 'wit_option_location', function ( $location, $name ) {
    if ( 'my_theme_options' === $name ) {
        $location['what']  = 'تنظیمات قالب';
        $location['where'] = 'پیشخوان ← تنظیمات قالب';
        $location['url']   = admin_url( 'admin.php?page=my-theme' );
    }
    return $location;
}, 10, 2 );

// نرمال‌سازی حروف هم‌شکل خودتان را اضافه کنید.
add_filter( 'wit_variants', function ( $variants, $needle ) {
    $variants[] = str_replace( 'أ', 'ا', $needle );
    return $variants;
}, 10, 2 );

// روی نتیجه‌ها پردازش اضافه انجام دهید.
add_filter( 'wit_results', function ( $results, $variants ) {
    return $results;
}, 10, 2 );
```

## محدودیت‌ها

فهرست صادقانه:

- **متنی که با کد ساخته می‌شود پیدا نمی‌شود.** اگر یک قالب یا افزونه رشته‌ای را مستقیم داخل کد چاپ کند، آن متن در فایل پی‌اچ‌پی است نه در دیتابیس. این افزونه عمداً فقط دیتابیس را می‌گردد: گشتن فایل‌های قالب وقتی قالب رمزگذاری‌شده یا فشرده باشد بی‌فایده است، و وقتی ابزار جست‌وجو ویرایشگر فایل هم باشد خطرناک است.
- **فقط برای المنتور حالت ویژه دارد.** صفحه‌سازهای دیگری که JSON را در postmeta ذخیره می‌کنند همچنان **پیدا** می‌شوند (جست‌وجوی JSON عمومی است) ولی نتیجه به ویرایشگر عادی وردپرس لینک می‌دهد نه به صفحه‌ساز.
- **ردیف‌های سریالایزشده بیشتر از حد option قابل ردیابی نیستند.** برای ابزارک‌ها نمونهٔ دقیق و ناحیه‌اش مشخص می‌شود؛ برای بلوک تنظیمات یک‌پارچهٔ یک قالب، خود option و صفحهٔ تنظیماتش را می‌گیرید، نه تک‌تک فیلدها.
- **جایگزینی متن ندارد.** عمدی است. این ابزار پیدا می‌کند؛ ویرایش با خود شماست. جایگزین‌کردن متن داخل یک option سریالایزشده یکی از راه‌های خراب‌شدن سایت است.
